# tx-pr-auditor — Business Logic Analysis

## Purpose

This document describes the business decisions currently owned by `tx-pr-auditor`. These rules must remain in the standalone Python skill and must not be interpreted or reproduced by AI Worker Platform.

Sources reviewed:

- `skills/tx-pr-auditor/SKILL.md`
- `skills/tx-pr-auditor/references/business-logic.md`
- `skills/tx-pr-auditor/references/current-inputs.md`
- Current `scripts/audit_final_po.py` pipeline

## Business Boundary

The auditor answers one question:

> Does each submitted Final PO row agree with entitlement already generated by `create-pr-cd`?

Sources of truth:

- Generated ECC: expected entitlement.
- Final PO: submitted claim population and submitted line details.

Not sources of truth:

- iEPMS/Site PR-PO data.
- PR model.
- Reconstructed entitlement rules.
- PR number alone.

The auditor must not call or imitate `create-pr-cd` during focused audit execution.

## Decision Order

```text
Read explicit Final PO and ECC inputs
  -> map workbook fields
  -> canonicalize identity and quantities
  -> optionally filter Final PO by dispatch period
  -> match site/DU entitlement
  -> resolve DU model and scope identity
  -> validate subcontractor
  -> validate item code
  -> mark valid claims pending quantity
  -> consume expected quantity deterministically
  -> write classifications and evidence
```

Classification checks occur before quantity consumption. Invalid or Wrong rows can never make a later valid row Duplicate.

## 1. Input Population

The caller supplies explicit paths for:

- One Final PO workbook.
- One or more generated ECC files or directories.

The skill must not discover inputs by scanning arbitrary workspace locations.

When both audit-period parameters are supplied, only Final PO rows whose Dispatch Date matches the requested year and month are audited. ECC entitlement is still loaded as the comparison population.

## 2. Workbook Mapping

Final PO layout is auto-detected from supported worksheet/header combinations, with explicit overrides allowed. The field map accepts current multilingual headers and retained historical mojibake aliases.

Generated ECC defaults to the `details` worksheet and maps site, DU, scope, item, subcontractor, quantity and DU lineage fields.

Field names and aliases are domain compatibility rules. They belong in the skill, even when a platform upload form describes the required file.

## 3. Canonical Identity

The auditor normalizes:

- Physical site code.
- Logical DU code.
- Submitted and expected item code.
- Submitted and expected subcontractor.
- Submitted and expected quantity.
- Dispatch sorting fields.
- Scope and DU identity evidence.

Generated ECC identity is resolved from explicit DU model/profile/view fields when present and may fall back to approved filename evidence. Final PO identity may be inferred from project, project code, product-model remarks and logical-site information.

The local DU registry defines approved Project + DU Model identities and their accepted profile/view lineage. Identity must fail closed when evidence is unknown, conflicting or ambiguous.

## 4. Entitlement Matching

For each Final PO row:

1. Build candidate keys from physical site code and logical DU.
2. Find generated ECC rows for the first matching candidate key.
3. If Final PO provides a resolved DU identity, restrict resolved ECC candidates to that identity while retaining unresolved evidence for validation.
4. If Final PO identifies a scope, restrict candidates to that scope.
5. Find exact item-code candidates.
6. If a submitted subcontractor is present, narrow exact item records to that subcontractor.
7. Preserve all relevant source workbook, sheet and row evidence.

Matching must not pool entitlement across unresolved DU models, scopes or subcontractors.

## 5. Classification Priority

The effective priority is:

1. `Abnormal - Invalid PO`
2. `Abnormal - Wrong PO`
3. `Abnormal - Duplicate PO`
4. `Normal`

The Python engine checks specific Invalid conditions before Wrong and quantity resolution.

## 6. Invalid PO

`Abnormal - Invalid PO` means the claim cannot be validated against a uniquely trustworthy entitlement context.

| Reason code | Business condition |
| --- | --- |
| `INVALID_NOT_IN_CREATE_PR_CD_OUTPUT` | No generated ECC entitlement exists for submitted site or DU |
| `INVALID_CONFLICTING_DU_IDENTITY` | Model, profile, view, project or filename identity evidence conflicts |
| `INVALID_UNKNOWN_DU_MODEL` | ECC entitlement is not associated with an approved DU identity |
| `INVALID_AMBIGUOUS_DU_MODEL` | Site/item entitlement spans multiple DU models without a resolved Final PO identity |
| `INVALID_AMBIGUOUS_SCOPE` | Site/item entitlement spans multiple scopes without a resolved submitted scope |
| `INVALID_SUBCON_CHANGED` | Submitted subcontractor differs from expected site/item entitlement |
| `INVALID_AMBIGUOUS_SUBCONTRACTOR` | Exact item entitlement spans multiple subcontractors and Final PO does not identify one |

Invalid rows consume zero expected quantity.

Subcontractor mismatch has priority over Wrong Item when the submitted subcontractor is already inconsistent with the site's expected entitlement.

## 7. Wrong PO

Use `Abnormal - Wrong PO` with `WRONG_LINE_ITEM_MAPPING` when:

- A trustworthy entitlement context exists for the submitted site/DU.
- The submitted subcontractor does not already make the claim invalid.
- The submitted item code is not present in that entitlement context.

Wrong rows consume zero expected quantity.

## 8. Pending Quantity

A row reaches internal `PENDING_QUANTITY` only after:

- Entitlement exists.
- DU identity is resolved and unambiguous.
- Scope is resolved and unambiguous.
- Item code matches.
- Subcontractor matches or is unambiguous.

This is an internal transitional state, not a final user classification.

Expected quantity is the sum of exact matching ECC entitlement rows after identity, scope, item and subcontractor restrictions.

## 9. Quantity Consumption

Valid claims are processed in deterministic ascending order:

1. Dispatch Date.
2. Request Number.
3. Dispatch Order Number.
4. PO Line Number.

Entitlement is consumed within a key made from:

- Site or DU key.
- DU identity.
- Scope.
- Item code.
- Normalized expected subcontractor.

This prevents quantity from leaking across sites, models, scopes, items or subcontractors.

For each valid row:

```text
available = max(expected quantity - previously consumed normal quantity, 0)
normal quantity = min(submitted quantity, available)
duplicate quantity = max(submitted quantity - normal quantity, 0)
```

Only `normal quantity` consumes entitlement.

## 10. Normal and Duplicate Outcomes

| Final classification | Reason code | Condition |
| --- | --- | --- |
| `Normal` | `NORMAL_FULL` | Entire submitted quantity is within remaining entitlement |
| `Abnormal - Duplicate PO` | `DUPLICATE_PARTIAL_QUANTITY` | Some submitted quantity is entitled and the remainder exceeds it |
| `Abnormal - Duplicate PO` | `DUPLICATE_FULL_QUANTITY` | No remaining entitlement is available |

A partially duplicated source row is not split into multiple rows. The original submitted quantity is preserved, while `Normal Quantity` and `Duplicate Quantity` explain the allocation.

## 11. Evidence Requirements

Every result must preserve enough evidence to explain the outcome:

- Source Final PO row and original columns.
- Site, DU, project, scope and DU lineage.
- Submitted item, description, subcontractor and quantities.
- Request/order/line/date ordering fields.
- Expected item, quantity and subcontractor.
- Generated ECC filename, worksheet and row evidence.
- Classification, reason code, normal quantity, duplicate quantity and explanation.

Evidence is part of the business result, not a platform log.

## 12. Output Rules

Primary output:

- `PR_Audit_Result.xlsx` with original Final PO columns plus audit columns.

Optional outputs:

- JSON audit summary.
- Timestamped copied ECC workbooks with appended audit status and evidence columns.

Source workbooks must never be modified. An ECC row without an exact Final PO item match is labeled `NOT_IN_FINAL_PO` in an annotated copy; this does not rewrite entitlement.

## 13. Fail-Closed Principles

- Missing entitlement is not assumed valid.
- Unknown identity is not inferred from an unrelated model.
- Conflicting lineage is not resolved by arbitrary precedence.
- Entitlement is not pooled across ambiguous models, scopes or subcontractors.
- Invalid and Wrong rows never consume quantity.
- Source data is never mutated.
- Audit evidence must remain traceable to source rows.

## 14. Relationship to Combined Workflow

The current platform generates TSS and TI ECC from iEPMS before invoking the auditor. That sequence is product orchestration, not auditor business logic.

In the target architecture:

- The focused `tx-pr-auditor` continues to accept Final PO + ECC only.
- Separate jobs may provide ECC outputs to the auditor; or
- A dedicated composite Python skill may own entitlement generation plus audit.

The generic platform must not embed the sequence or pass iEPMS into the focused auditor.

## 15. Refactor Invariants

The thin-wrapper refactor is correct only if:

- The same Final PO/ECC fixture produces the same classification and reason code per source row.
- Identity, scope and subcontractor ambiguity remain fail-closed.
- Deterministic consumption order remains unchanged.
- Normal and duplicate quantities remain unchanged.
- Evidence and source lineage remain complete.
- Original workbooks remain byte-for-byte unchanged.
- Platform code contains no audit field mapping, reason-code priority or quantity logic.

## 16. Business Decisions Still Required

- Define an explicit version-compatibility policy between the auditor DU registry and `create-pr-cd` ECC identity fields.
- Confirm the production policy for Final PO rows with zero, negative or malformed submitted quantity.
- Confirm how missing submitted subcontractor should be treated when only one expected subcontractor exists; current code permits the unambiguous case.
- Confirm the required user-facing behavior when a period filter matches no Final PO rows.
- Define limits and operational policy for very large Final PO/ECC batches.
