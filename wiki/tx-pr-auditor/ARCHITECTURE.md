# tx-pr-auditor — Architecture

## Purpose

`tx-pr-auditor` is a standalone Python domain engine that validates submitted Final PO rows against ECC entitlement generated by `create-pr-cd`.

Its boundary is deliberately downstream:

```text
Final PO + generated ECC entitlement
  -> canonical comparison
  -> audit classification
  -> quantity and duplicate resolution
  -> evidence-backed audit report
```

It must not read iEPMS or the PR model. Re-reading them would create a second entitlement engine and risk divergence from `create-pr-cd`.

## Skill Relationship

```text
iEPMS
  -> create-pr-cd
  -> generated ECC entitlement
  -> tx-pr-auditor
  -> PR_Audit_Result.xlsx

Final PO ------------------------------^
```

`create-pr-cd` owns entitlement generation. `tx-pr-auditor` owns the comparison of submitted PO data to that entitlement.

## System Boundary

### Skill ownership

- Detect Final PO worksheet and header layout.
- Map Final PO and ECC fields into canonical records.
- Normalize site, DU, item, subcontractor and quantity values.
- Resolve DU identity and source lineage.
- Match submitted rows to ECC entitlement.
- Detect ambiguous DU, scope or subcontractor evidence.
- Classify Invalid, Wrong, Duplicate and Normal rows.
- Consume expected quantity deterministically.
- Preserve evidence and write audit outputs.

### Platform ownership

- HTTPS, authentication and generic request handling.
- Generic declared file constraints.
- Isolated workspace and safe paths.
- Process supervision, timeout and cancellation.
- Job metadata, progress transport and output delivery.
- Structural validation of manifest, input and result envelopes.

The platform must not know Final PO headers, audit reason codes, classification priority or quantity-consumption rules.

## Current Internal Architecture

The current `scripts/audit_final_po.py` implements a centralized batch pipeline:

```text
Workbook Reader
  -> Field Mapper
  -> Canonical Builder
  -> Expected ECC Matcher
  -> Audit Engine
  -> Duplicate Resolver
  -> Report Writer
```

Stages return new datasets and the orchestrator controls their order. Important model types include Final PO records, expected ECC records, expected matches and audit results.

## Classification and Quantity Model

Classification priority:

1. `Abnormal - Invalid PO`
2. `Abnormal - Wrong PO`
3. `Abnormal - Duplicate PO`
4. `Normal`

Only otherwise-valid claims consume expected quantity. Consumption is ordered by Dispatch Date, Request Number, Dispatch Order Number and PO Line Number. Invalid and Wrong rows consume nothing.

The skill fails closed for missing entitlement, unknown/conflicting identity and unresolved ambiguity.

## Current Platform Coupling

The current platform does more than run the focused auditor:

- Accepts Final PO and iEPMS uploads in one job.
- Hardcodes `create-pr-cd` TSS and TI execution.
- Stages intermediate ECC files.
- Builds auditor-specific CLI flags.
- Defines domain-specific progress stages.
- Discovers fixed output names and normalizes audit classifications.

This is a convenient composite product workflow, but the orchestration is not appropriate for a generic platform core.

## Target Runtime Architecture

Focused auditor execution:

```text
POST /skills/tx-pr-auditor/jobs
  -> Final PO + ECC uploads
  -> generic isolated workspace
  -> input/input.json
  -> python <entrypoint> --input-manifest input/input.json
  -> NDJSON progress
  -> PR audit outputs + result.json
  -> generic validation and delivery
```

If the product must retain a single iEPMS + Final PO job, implement a separate standalone composite Python skill such as `tx-pr-audit-workflow`. That skill—not the platform—owns `create-pr-cd TSS -> create-pr-cd TI -> tx-pr-auditor` sequencing and dependency versions.

## Safety Invariants

- ECC output is the only entitlement source.
- iEPMS and PR model are not auditor inputs.
- Source Final PO and ECC files are never modified.
- Ambiguous evidence fails closed.
- Invalid and Wrong rows do not consume quantity.
- All classification evidence remains traceable.
- Generated paths stay inside the declared workspace.
